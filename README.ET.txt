Notes on the ET llvm target

1. The target is a variant of RISCV enabled with the
   target triple riscv64-unknown-elf (the default target
   in the usual build).

   The usual build is performed setup by "et/build.sh"


2. The MC layer is complete for Minion (no support for Maxion yet)
   and is selected using the mcpu option set to "et-soc1-min".
   
   The assembler is invoked
       clang -c -mcpu=et-soc1-min -mabi=lp64f <input.s>
   To disassemble:
       llvm-objdump --mcpu=et-soc1-min -d <input.o>

3. Most instructions are available to C programs via buitlins
   which have the format:
   	 __builtin_riscv_<name>(<parameters>)
   where <name> is the lower case opcode with "." replaced with "_".
   Thus, "__builtin_riscv_fadd_ps" for "fadd.ps".

   The arguments for the builtins are the same as the inputs
   to the instruction. Default type for parameters and
   return types is "long". This is true for mask values as
   well although only the low 8 bits are used.

   Vector types are
      	  float __attribute__((vector_size) (32))
   for ".ps" instructions and 
   	  int __attribute__((vector_size) (32))
   for ".pi" instructions.

   Unlike the assembly instructions, the implicit "m0" operand
   is explicit for builtin functions and rounding modes are
   required. Also, for instructions which use m0 to selectively
   update the destination register, the first operand to the
   builtin is the vector value used for unselected values. Thus
   an example for fadd_ps might be:

float __attribute((vector_size(32)))
test_fadd_ps(float __attribute((vector_size(32))) in,
             float __attribute((vector_size(32))) rs1,
             float __attribute((vector_size(32))) rs2, long m0) {
#define RTZ 1 
  return __builtin_riscv_fadd_ps(in, rs1, rs2, RTZ, m0);
}

  The result value is the same as "in" for lanes not selected by m0.

  Immediate values must be manifest constant operands (after preprocessing).

  There is no builtin support for "mova.x.m" and "mova.m.x"


4. Builtins are translated to LLVM IR intrinsics with essentially the
   same signature. Thus for "fadd.ps" this would be:

def int_riscv_fadd_ps : 
  GCCBuiltin<"__builtin_riscv_fadd_ps">,
  Intrinsic<[llvm_v8i32_ty],
            [llvm_v8i32_ty,llvm_v8i32_ty,llvm_v8i32_ty,llvm_i64_ty,llvm_i64_ty],
            [ImmArg<ArgIndex<3>>,IntrNoMem]>;

  There is no intrinsic support for "mova.x.m" and "mova.m.x"

5. Each instruction with implicit registers has a companion pseudo
   instruction with those register explict. Code generation (currently
   limited to intrinsics) use those pseudo and which are translated to
   the target instrctions. These instructions have an "_EX" suffix so
   "FADD_PS" is the opcode for the fadd.ps instruction and
   "FADD_PS_EX" is the explicit pseudo instruction opcode.

6. Supporting scripts are in et/python

   intrinsics.py -- read tblgen spec and builts specs for builtins,
       intrinsic definitions, and intrinsic DAG Isel patterns. The outputs
       of this function are stored in the repo
   Makefile -- run intrinsics.py and update sources files
   gen_asm.py -- generate an assembly file with random examples
       of the extension instructions
   verify.py -- verify correct encoding for assembly of extension
       instructions generated by gen_asm.py
   gen_ctest.py -- generate a C file with small functions to exercise
       all of the builtins
   test.sh -- shell script to use the above scripts to test implementation
